The mental model

zdev is the attention layer over a fleet of AI coding agents running in tmux. It answers one question continuously: who needs me next?

A daemon (zdevd) watches tmux in control mode, classifies every session's agent state — waiting, working, finished, dead — and renders a per-project sidebar plus a ranked triage queue. It never wraps an agent, opens a network listener, or builds a web UI. Three layers, three jobs:

LayerQuestionTool
zdevwho needs me now?sidebar, triage, notifications
beads (bd)what's ready next?per-initiative work graph
Jirawhat does the team see?the tracker above both

The workspace

The disk is the registry. With ZDEV_PROJECTS_DISCOVER=1, the layout of ~/workspace defines what zdev supervises — no list to maintain:

~/workspace/
  projects/<repo>              canonical checkouts — mainline truth, reviews
  initiatives/<name>/          one initiative (see below)
  <dir with .git>              root repos (zdev, dotfiles, …)
RuleBecomes a row?
root dir with .gityes — standalone project
projects/<dir> (any dir)yes — canonical pool
initiatives/<name>yes — the initiative's home row
initiatives/<name>/<dir> with .gityes — member clone
initiatives/<name>/notes (no .git)no — knowledge, not work

The daemon watches the workspace: create or delete a directory and the corresponding row follows within seconds. No config edit, no restart.

Why is this row here? zdev --list-projects -v prints name → origin for every row — declared, favorite, or the discovery rule that matched. The audit trail that keeps the implicit convention honest.

~/.config/zdev/projects holds overrides only: favorites (append  * — started by zdev up, never reaped) and off-convention paths.

Initiatives

An initiative is the unit of value delivered. It spans repos, lives exactly as long as delivery requires, and its scope drifts as work reveals itself. Mechanically:

initiatives/<name>/
  INITIATIVE.md     identity: intent, tracker links, dated decisions, outcome
  notes/            the knowledge base (never a sidebar row)
  .beads/           bd work graph (optional but recommended)
  <repo>/           FULL CLONE of projects/<repo>, branch <name>/<thing>

Why full clones (not worktrees)?

  • Two initiatives can hold the same repo simultaneously, isolated.
  • A clone can check out mainline — a worktree never could while canonical held it.
  • Repo state is fully isolated: agent git surgery in one initiative cannot corrupt canonical or a sibling. Local clones hardlink objects, so disk is cheap.
  • The trade: a clone's mainline is only as fresh as its last git fetch.

The lifecycle

# start
mkdir -p ~/workspace/initiatives/<name>/notes
# write INITIATIVE.md; commit in the initiatives repo; optional: bd init
# (the journal repo itself is scaffolded by install.sh and should have a
#  private remote — `zdev doctor` warns while commits are laptop-only)

# add a repo — this is the ENTIRE operation; the row appears by itself
# (local source = speed + hardlinks only; gh repo clone works identically —
#  all durable linkage runs through the GitHub remote, not projects/)
git clone ~/workspace/projects/<repo> ~/workspace/initiatives/<name>/<repo>
git -C …/<repo> remote set-url origin git@github.com:org/<repo>.git
git -C …/<repo> checkout -b <name>/<thing>

# reintegrate: ordinary PRs from the clone. when the branch lands:
rm -rf ~/workspace/initiatives/<name>/<repo>      # row disappears

# wind down: fill INITIATIVE.md's Outcome, commit, delete the directory —
# the initiatives repo's history is the journal that outlives it.
Rules of thumb. Canonical checkouts stay boring (never do initiative work there — reviewing a colleague's PR is fine and needs no initiative). Only clone a repo when work actually starts. A clone whose branch merged >2 weeks ago is rot — delete it, don't nurse it. The /initiative skill in Claude walks all of this.

  ◐ zdev                     working (spinner)

  • Each initiative's name renders in its own stable color — recognizable before it's read. The gutter matches.
  • Grouped rows show the leaf (pay-app); the switcher keeps full paths for targeting.
  • Markers: ● waiting · ◐◓◑◒ working · ◆ finished · ✗ dead · · idle. Full legend: zdev-show --legend.
  • Rows order: grouped sections first (alphabetical), ungrouped singles last. Row positions are stable — spatial memory is a contract.

Attention & notifications

Waits escalate through tiers; each fires at most once per wait:

AgeMessageSuppressed when…
60swaiting 1m…you're attached to any session (defers; folds into 5m)
5mstill waiting (5m)…you're attached to that session, or acked it
15mSTUCK (15m)

So in practice the first thing you hear is the 5-minute tier — zdev only speaks about work you've genuinely left. Delivery is the spoken "<project> needs you" (via ZDEV_NOTIFY_CMD → ~/.config/zdev/notify-backend.sh); every fire logs one line to ~/Library/Logs/zdev/notify-backend.log. Mute with M-o or zdev notify mute 1h — the mute gates everything the daemon fires. Agent death notifies once, immediately, regardless of presence.

Landing readiness

zdev review (and ZDEV_SIDEBAR_REVIEW=1 for the sidebar gauge) shows reintegration debt per repo, longest-rotting first: ◆ ready to land (PR open, CI green, clean tree) · ✗ needs a fix · ⌁ uncommitted work that will rot. Initiative clones resolve to their canonical repo, so debt aggregates correctly across checkouts.

Agent supervision

  • State detection: Claude Code hooks (zdev-notify) drive waiting/working/finished; death detection catches unclean exits — ✗ tops the triage queue.
  • zdev run <project> "<prompt>" spawns a supervised agent loop in its own window — the actuator for triggers and MCP.
  • Agent Teams (ZDEV_TEAM_WINDOWS=1): teammates auto-move to their own windows, nest under the lead's row, and are individually jumpable from M-p.
  • Reaping: idle sessions die after ZDEV_REAP_AFTER_HOURS (8h default); favorites are exempt. Rows persist as absent — reaping is about tmux hygiene, not scope.

Context in Claude

Claude Code loads CLAUDE.md from every directory above the cwd, so the workspace teaches itself — a session at an initiative home (or in any clone under it) automatically inherits:

~/workspace/CLAUDE.md                the map (containers, conventions)
~/workspace/projects/CLAUDE.md       canonical-pool rules
~/workspace/initiatives/CLAUDE.md    the initiative playbook
…/initiatives/<name>/CLAUDE.md       → AGENTS.md: bd conventions, specifics

Plus the /initiative skill for the full lifecycle, and bd's bd prime for work-graph context at session start.

Config reference

statuses flap or freezetail ~/Library/Logs/zdev/zdevd.log; check you're not working inside zdevd-watcher (daemon-internal session)
