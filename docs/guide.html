The mental model

zdev is the attention layer over a fleet of AI coding agents running in tmux. It answers one question continuously: who needs me next?

A daemon (zdevd) watches tmux in control mode, classifies every session's agent state — waiting, working, finished, dead — and renders a per-project sidebar plus a ranked triage queue. It never wraps an agent, opens a network listener, or builds a web UI. Three layers, three jobs:

LayerQuestionTool
zdevwho needs me now?sidebar, triage, notifications
beads (bd)what's ready next?per-initiative work graph
Jirawhat does the team see?the tracker above both

The workspace

The disk is the registry. With ZDEV_PROJECTS_DISCOVER=1, the layout of ~/workspace defines what zdev supervises — no list to maintain:

~/workspace/                   the workspace root is ALSO the journal repo
  <dir with .git>              root repos (zdev, dotfiles, …) — plain rows
  projects/.zdev               marked group (drawer) — the marker itself
  projects/<repo>              …every child dir rows — canonical checkouts
  <name>/INITIATIVE.md         marked group = an initiative (see below)

The tree mirrors the disk — no path is special. But group-ness is never inferred from shape: every directory at the workspace root is resolved by asking what marker file it contains, and there are exactly three outcomes.

The three outcomes

Marker presentWhat it becomes
.gita project — one plain row (zdev, dotfiles)
INITIATIVE.mda group, and specifically an initiative: the directory itself rows as the group's home, plus one row per child that has .git (so notes/ never rows)
.zdeva group, and specifically a drawer: every child directory rows; the group directory itself does not (no home — nothing claimed)
none of the aboveinvisible — no rows at all, even if it has children. This is deliberate: a stray non-git directory (archive/, a Downloads-ish folder) must never silently become sidebar rows

INITIATIVE.md alone is sufficient to make a directory a group — it does not also need .zdev. The two group markers are mutually exclusive in practice (a directory is either an initiative or a drawer), and a directory with neither is simply not part of the registry. zdev doctor scans for directories that would have produced rows under the old implicit rule but are now invisible, and prints the exact one-liner to fix each.

What .zdev is

.zdev is a TOML file, and today an empty file is completely normal — its mere existence is the marker. Discovery (the bash layer in bin/zdev) only checks whether it exists; it never parses or reads its contents, so any TOML you put in it today is inert. It's reserved for group metadata in a future release — display name, colour, per-group collapse behaviour — and unknown keys will always be ignored. Until then, touch <dir>/.zdev is the entire operation.

The two group markers answer different questions, and both can eventually carry metadata:

  • .zdev answers "is this directory a group?" — machine-oriented, currently existence-only, future home for group display metadata.
  • INITIATIVE.md answers "is this group an initiative?" — human-oriented markdown: intent, tracker links, dated decisions, and an outcome at wind-down. This one is read today, by you and by /zdev:initiative.

Creating each outcome is a one-liner, and all three appear (or disappear) in the sidebar within seconds — the daemon watches the workspace:

# a drawer — mark it, then put repos in it
mkdir -p ~/workspace/scratch && touch ~/workspace/scratch/.zdev
git clone <url> ~/workspace/scratch/thing

# an initiative — the same, but INITIATIVE.md is the mark instead
mkdir -p ~/workspace/marketplace/notes
$EDITOR ~/workspace/marketplace/INITIATIVE.md   # intent, tracker links

# promote a drawer to an initiative (or demote: delete the file)
touch ~/workspace/scratch/INITIATIVE.md

# a directory with no marker at all is invisible — no rows, no watching
mkdir -p ~/workspace/archive   # zdev never sees this

What the mark actually changes

Both are equally declared groups now — a drawer is no longer accidental scaffolding, so it does not render as one. In the sidebar and the M-p switcher a drawer's header looks exactly like an initiative's home row: same ╭/▸ glyph, its own stable PaletteFor identity hue, same bold, members hanging off a hued gutter. What differs between them is semantic, not visual:

Drawer (.zdev)Initiative (INITIATIVE.md)
Which children rowevery child directoryonly children with .git (so notes/ never rows)
Is the header's directory itself a real row?no — a label only; clicking it jumps to the first memberyes — its own directory is a row (the "home"), and you can zdev <name> to work at the initiative level
Journal trackingignored (contents are other repos' working trees)INITIATIVE.md, notes/, AGENTS.md, .beads/ versioned by the workspace journal
Collapse settingcontainers in [collapse]initiatives in [collapse]
Toolingnone — it's a folderthe /zdev:initiative skill: start, add repo, status, wind down
Rule of thumb. Mark a group as an initiative when the work has an identity worth remembering — a unit of value with intent, decisions, and an outcome that should outlive the directory. Mark it a plain drawer (.zdev) when it's just somewhere to keep checkouts. Leave it unmarked — invisible — when it isn't a zdev concern at all. A drawer costs nothing and can be promoted to an initiative later with one touch.

The rules in full, for reference:

RuleBecomes a row?
root dir with .gityes — standalone project
marked group <name>/ (has INITIATIVE.md)yes — the initiative's home row
<name>/<dir> with .git (marked initiative)yes — member clone
<name>/notes (no .git, marked initiative)no — knowledge, not work
marked drawer member (e.g. projects/<dir>, any dir, group has .zdev)yes — drawer row
root dir with no marker (no .git, INITIATIVE.md, or .zdev)no — invisible, regardless of what's inside it

The daemon watches the workspace: create or delete a directory inside a marked group and the corresponding row follows within seconds. No config edit, no restart. (An unmarked directory isn't watched at all — see below.)

Why is this row here? zdev --list-projects -v prints name → origin for every row — declared, favorite, or the discovery rule that matched. The audit trail that keeps the implicit convention honest.

~/.config/zdev/projects holds overrides only: favorites (append  * — started by zdev up, never reaped) and off-convention paths.

Migrating from an older zdev. Before this marker existed, any non-git root directory was a drawer. If you're upgrading, zdev doctor scans the workspace root and warns about every directory that has child directories but neither .git, INITIATIVE.md, nor .zdev — those rows just went invisible. The fix it prints is touch <dir>/.zdev (drawer) or adding INITIATIVE.md (initiative), whichever fits.

Initiatives

The ontology, settled: there is ONE structural concept — the group (a directory of members that folds behind a header), declared explicitly via .zdev or INITIATIVE.md. Every group has initiative functionality available; utilisation is optional. projects/ is a group that doesn't utilise it — marked with .zdev, not INITIATIVE.md, so it has no identity of its own, but it renders with the same visual standing as any initiative. An initiative is a group that does utilise it: the unit of value delivered, spanning repos, living exactly as long as delivery requires, its scope drifting as work reveals itself. The mark is the on-disk INITIATIVE.md — the workspace root is the journal repo, versioning every group's metadata via a whitelist gitignore. Mechanically:

~/workspace/<name>/
  INITIATIVE.md     identity: intent, tracker links, dated decisions, outcome
  notes/            the knowledge base (never a sidebar row)
  .beads/           bd work graph (optional but recommended)
  <repo>/           FULL CLONE of projects/<repo>, branch <name>/<thing>

Why full clones (not worktrees)?

  • Two initiatives can hold the same repo simultaneously, isolated.
  • A clone can check out mainline — a worktree never could while canonical held it.
  • Repo state is fully isolated: agent git surgery in one initiative cannot corrupt canonical or a sibling. Local clones hardlink objects, so disk is cheap.
  • The trade: a clone's mainline is only as fresh as its last git fetch.

The lifecycle

# start — writing INITIATIVE.md IS what makes the group an initiative
mkdir -p ~/workspace/<name>/notes
# write INITIATIVE.md; commit in the workspace journal; optional: bd init
# (the journal repo is scaffolded by install.sh and should have a
#  private remote — `zdev doctor` warns while commits are laptop-only)

# add a repo — this is the ENTIRE operation; the row appears by itself
# (local source = speed + hardlinks only; gh repo clone works identically —
#  all durable linkage runs through the GitHub remote, not projects/)
git clone ~/workspace/projects/<repo> ~/workspace/<name>/<repo>
git -C …/<repo> remote set-url origin git@github.com:org/<repo>.git
git -C …/<repo> checkout -b <name>/<thing>

# reintegrate: ordinary PRs from the clone. when the branch lands:
rm -rf ~/workspace/<name>/<repo>                  # row disappears

# wind down: fill INITIATIVE.md's Outcome, commit, delete the directory —
# the workspace journal's history is the record that outlives it.
Rules of thumb. Canonical checkouts stay boring (never do initiative work there — reviewing a colleague's PR is fine and needs no initiative). Only clone a repo when work actually starts. A clone whose branch merged >2 weeks ago is rot — delete it, don't nurse it. The /initiative skill in Claude walks all of this.

  • Each group's name — drawer or initiative alike — renders in its own stable color — recognizable before it's read. The gutter matches.
  • Grouped rows show the leaf (pay-app); the switcher keeps full paths for targeting.
  • Markers: ● waiting · ◐◓◑◒ working · ◆ finished · ✗ dead · · idle. Full legend: zdev-show --legend.
  • Row order: pure alphabetical — the tree mirrors the disk, groups and singles interleaved. Row positions are stable — spatial memory is a contract.

Attention & notifications

Waits escalate through tiers; each fires at most once per wait:

AgeMessageSuppressed when…
60swaiting 1m…you're attached to any session (defers; folds into 5m)
5mstill waiting (5m)…you're attached to that session, or acked it
15mSTUCK (15m)

So in practice the first thing you hear is the 5-minute tier — zdev only speaks about work you've genuinely left. Delivery is the spoken "<project> needs you" (via ZDEV_NOTIFY_CMD → ~/.config/zdev/notify-backend.sh); every fire logs one line to ~/Library/Logs/zdev/notify-backend.log. Mute with M-o or zdev notify mute 1h — the mute gates everything the daemon fires. Agent death notifies once, immediately, regardless of presence.

Landing readiness

zdev review (and ZDEV_SIDEBAR_REVIEW=1 for the sidebar gauge) shows reintegration debt per repo, longest-rotting first: ◆ ready to land (PR open, CI green, clean tree) · ✗ needs a fix · ⌁ uncommitted work that will rot. Initiative clones resolve to their canonical repo, so debt aggregates correctly across checkouts.

Agent supervision

  • State detection: Claude Code hooks (zdev-notify) drive waiting/working/finished; death detection catches unclean exits — ✗ tops the triage queue.
  • zdev run <project> "<prompt>" spawns a supervised agent loop in its own window — the actuator for triggers and MCP.
  • Agent Teams (ZDEV_TEAM_WINDOWS=1): teammates auto-move to their own windows, nest under the lead's row, and are individually jumpable from M-p.
  • Reaping: idle sessions die after ZDEV_REAP_AFTER_HOURS (8h default); favorites are exempt. Rows persist as absent — reaping is about tmux hygiene, not scope.

Context in Claude

Claude Code loads CLAUDE.md from every directory above the cwd, so the workspace teaches itself — a session at an initiative home (or in any clone under it) automatically inherits:

~/workspace/CLAUDE.md                the map + the initiative playbook
~/workspace/projects/CLAUDE.md       canonical-pool rules
~/workspace/<name>/CLAUDE.md         → AGENTS.md: bd conventions, specifics

Plus the /initiative skill for the full lifecycle, and bd's bd prime for work-graph context at session start.
