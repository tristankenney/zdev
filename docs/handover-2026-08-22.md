## The one-paragraph version

zdev could see the fleet but not rearrange the workspace around it. It now
can: a waiting agent's window links into wherever you're looking, and an
agent can ask for a viewport pane beside itself. Both go through pure
planners with the same guards, both are off by default, and both were
verified against a real tmux rather than only in table tests. Along the way
three pre-existing bugs surfaced and are fixed: a dead daemon nobody
noticed, an unguarded resize path that could discard your zoom or scroll
position, and a ghost session zdev was sustaining with its own sidebar pane.

## Before anything else: it was broken when I got here

The daemon had been **dead since the checkout was renamed** from
`~/workspace/zdev` to `~/workspace/zdev-tmux`. launchd was exec'ing a path
that no longer existed — exit 78 `EX_CONFIG`, parked in the penalty box —
while `make install` kept printing success. Cause: `$(PLIST_BUILT)` depended
only on the template and the Makefile, and a rename touches neither, so make
kept re-linking a stale plist.

`zdev-doctor` missed it twice over, because `pgrep -x zdevd` matches on
process *name* and so returned all sixteen `zdevd mcp` children.

Both fixed (`3a87276`). The lesson worth keeping: **a rename invalidates every
generated file that baked a path in, and nothing in the build output says so.**
`SUBST_STAMP` now makes `REPO_ROOT`/`HOME` themselves a prerequisite.

## The five load-bearing design decisions

Change these only deliberately; each is the answer to a specific failure.

1. **Windows are free; panes are zero-sum.** A window is off-screen until
   visited and invisible to the agent in it, so linking needs only a dwell. A
   pane takes space from the agent you are mid-sentence with, so it needs a
   budget, a priority order and an eviction rule.
2. **`link-window`, never `new-window`.** `unlink-window` without `-k` refuses
   when a window has only one link. The planner never emits `-k`, so no
   sequence of plans can destroy an agent's window. That refusal *is* the
   safety net — verified live, not assumed.
3. **The shell is the donor; the agent is sacred.** Splitting the shell means
   the agent's geometry never changes, so its TUI never reflows. That removes
   "opening a pane scrambled my prompt" by construction, not by guard.
4. **The agent gets an output channel, not a shell.** It receives a *derived*
   path and appends to it; the daemon owns the tail. No new execution surface,
   and `/etc/shadow` can never be the target. Caps are structural: one request
   *file* per session is the one-pane cap, and the session comes from the
   *filename*, so an agent cannot reach another project's window.
5. **A turn ends only on positive evidence.** See the top open risk below.

## Open risks, ranked

### 1. Turn-scoping rests entirely on the Stop hook

The first cut inferred "turn over" from the agent looking idle. The first
real-fleet run proved that wrong: `AttWorking` decays after
`hookWorkFreshSec` (180s, `internal/hub/attention.go:162`), so a long quiet
turn reads as idle and the pane would be pulled out from under you mid-read.

Now `bin/zdev-notify` withdraws the request on the Stop hook, with only two
backstops, both positive signals: the agent died, or the request aged out.
**The exposure is the inverse** — if a turn ends without the Stop hook firing
(hooks not installed, agent killed oddly), the pane lingers up to
`ZDEV_PANES_MAX_AGE`. Nothing worse than a stale viewport, but watch it.

**If a pane retires mid-turn, that is the finding.** Bind the lifetime to a
harder signal rather than tuning the freshness window.

### 2. Index reservation is impossible, and the doc used to claim otherwise

Probed on 3.7b: with `renumber-windows on` (your setting), closing any window
compacts the space — a link placed at `:90` became `:2`. `LinkIndex` is a
*request*. Everything downstream keys off `window_id`. **Nothing may navigate
to a zdev link by index.**

### 3. Untested: the timer-arming path

`TopoNextDeadline`'s arithmetic is covered. The ~15 lines in `Run` that arm a
timer *from* it are not. Small and readable, but unproven.

### 4. No eventlog trail

Topology leaves only `slog` lines. The first time a surface appears and you
cannot reconstruct why, that is the trigger to move inside the hub (below).

## The zdev-core integration decision (recorded, not deferred)

All of this deliberately sits **outside `internal/hub`**: the reconciler
registers as an ordinary `hub.Subscriber`, and the request channel is a file
channel. That keeps every hub invariant out of play for a feature still
deciding what it is.

Two triggers, either sufficient, written up in the design note's Decisions
section:

1. **A topology decision must be consistent with hub state at one instant.**
   The phase 3–4 row budget and eviction order will require this; a file
   channel cannot be read transactionally with the state that gates it.
2. **A surface appears and `events.ndjson` cannot explain why.**

Until one fires, outside-the-hub is a feature, not debt. When one does, the
move gets reviewed against `.claude/agents/hub-invariants-reviewer.md`.

## Continuation update

Phase 3 is now implemented in the working tree: a project with listening ports
earns a `logs · runner` row when `ZDEV_PANES=1` and
`ZDEV_PANES_LOGS_COMMAND` is configured. Closing it suppresses it until the
runner cycles down then up. The generic core infers runner state but leaves the
logs command configurable rather than hard-coding the private runner. The row
uses its own `@zdev-logs` tag and therefore coexists with requested agent
viewports.

## Two diagnoses worth remembering

**The ghost session.** A `zdev` sidebar row nobody could account for. Cause:
tmux closes a window when its last pane exits and a session when its last
window closes — but a sidebar pane defeats both. When the shell and agent
exited, the renderer kept the window and therefore the session alive, and the
empty session then rowed itself as a project. A ghost sustained by the very
surface meant to report on it. `PlanTeamReap` already names this failure for
member windows; this was the same thing at session scope. `Plan` now reaps a
window whose only panes are zdev's own.

**Test isolation was fake.** Once the tmux.conf guard resolved, scratch tmux
servers in the live tests began inheriting the real zdev hooks and growing a
sidebar pane — so the earlier passes were an artifact of the *broken* guard.
Every scratch server now starts `-f /dev/null`, which also dropped
`base-index 1` and forced the tests onto window *names*. Strictly better
isolation than before.

28 new table-driven tests across the five new test files, plus four real-tmux
live tests. Notable property tests: the topology planner never emits
`kill-window` or a forced unlink; the pane planner only ever kills panes it
tagged itself and never one the operator is sitting in; both planners converge
(re-planning against the world they produced is a no-op).

**How to actually try it:** see the design note, or ask — the fastest path is
the pane feature, which you can drive by hand with `zdevd pane open` and a
`printf >> $STREAM`, no agent required.

## Bugs found by running it rather than reading it

Worth noting as a pattern, since all four were invisible to review:

1. Flags emitted *after* the verb in a generated command — `flag.Parse` stops
   at the first positional, so they were swallowed into a usage error inside a
   pane nobody was looking at. Same trap hit the CLI and the MCP tool.
2. `TopoSignature` called a predicate needing a tmux-resolved field that the
   snapshot-only gate does not have, so it was permanently empty and would
   have wedged the reconcile path shut after its first pass.
3. A 2s reconcile ticker, rejected by `check-no-daemon-fork.sh` — correctly, a
   heartbeat burns the idle budget `bench-idle` defends.
4. The index-reservation claim, falsified by a five-minute tmux probe *after*
   it had already been written into the roadmap as a mitigation.
